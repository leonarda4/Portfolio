# Machine readability and discoverability

## Original rendering problem

The site is a Vite-built React single-page application. `src/main.jsx` mounted React into an empty `#root`, and `src/App.jsx` selected project case studies from the URL hash. As a result, the production response initially contained metadata and an empty application root. The substantive homepage and project copy only appeared after JavaScript ran, and projects did not have independent canonical URLs.

The production build now prerenders semantic content into the initial HTML. React still mounts on that content and preserves the existing interactive experience. Public projects also have clean, stable routes that work when requested directly.

## Content sources and generation

The build reads these existing public sources:

- `src/content/profile.js` for the public identity, introduction, contact address, and resume link.
- `src/content/about-collage.js` for the public background and education notes.
- `src/content/project-one.json` through `src/content/project-four.json` for project pages.

`npm run build` runs Vite and then `scripts/generate-machine-readable.js`. The generator creates the prerendered pages, metadata, structured data, sitemap, crawler policy, Markdown pages, and JSON index from those sources. Hidden `pending` blocks, `editorialNotes`, and `coverBrief` fields are excluded from public machine-readable outputs.

When adding or updating a project:

1. Add the public project content to the corresponding `src/content/project-*.json` file.
2. Add the JSON file to the `projectFiles` list in `scripts/generate-machine-readable.js`.
3. Keep the existing React page renderer and the generator in sync when introducing a new block type. Add its meaningful text and media descriptions to the generated HTML and Markdown.
4. Run `npm run build` and `npm run test:machine-readability`.

Update public profile and About content in their source files. Do not copy content into generated files in `dist`; they are regenerated on every build.

## Public routes and representations

| URL | Format | Purpose |
| --- | --- | --- |
| `/` | HTML | Prerendered homepage, About notes, work links, contact |
| `/projects/{slug}/` | HTML | Prerendered case study and hydrated React experience |
| `/projects/{slug}.md` | Markdown | Case study text and media descriptions |
| `/llms.txt` | Markdown | Concise portfolio and project index |
| `/llms-full.txt` | Markdown | Homepage background and complete project text |
| `/portfolio.json` | JSON | Structured owner, background, professional experience, and projects |
| `/portfolio.schema.json` | JSON Schema | Schema for `portfolio.json` |
| `/robots.txt` | Text | Public crawler access policy and sitemap link |
| `/sitemap.xml` | XML | Canonical homepage and project URLs |
| `/404.html` | HTML | Static-host not-found page |

Markdown project files are served as `text/markdown` by the included Node server. The site source is generated by the build and can also be hosted statically if the host serves directory `index.html` files and exposes the generated text, JSON, XML, and 404 files.

## Metadata and structured data

The homepage has canonical, description, Open Graph, and Twitter card metadata, plus a JSON-LD graph for the portfolio owner, website, and profile page. Each project has unique title and description metadata, its canonical URL, Open Graph fields, and a `CreativeWork` JSON-LD entity connected to the owner with a stable `@id`.

The portfolio JSON includes only information already published in the page content. The education field preserves the text of the existing About notes rather than inferring institution details. The Tomsoft experience entry is derived from its published role, project period, summary, and canonical case-study URL. Awards, publications, external professional profiles, and other details without supporting public content are omitted.

## Crawler policy

The generated `robots.txt` allows general access and user-requested or search crawlers while excluding the model-training crawlers `GPTBot` and `ClaudeBot`. It allows `OAI-SearchBot`, `ChatGPT-User`, `Claude-SearchBot`, `Claude-User`, `PerplexityBot`, and `Perplexity-User`. These rules express crawler preferences, not access control, and do not guarantee that a crawler will visit or index the site.

The user-agent distinctions follow the current operator documentation:

- [OpenAI crawler documentation](https://developers.openai.com/api/docs/bots)
- [Anthropic crawler documentation](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler)
- [Perplexity crawler documentation](https://docs.perplexity.ai/docs/resources/perplexity-crawlers)

The policy disallows `/api/` from automated crawling. The public website's interactive endpoints are not portfolio content. No unpublished project routes are added to the sitemap.

## Deployment requirements and limitations

The generated canonical domain is `https://leonardalovric.com`. This repository cannot configure DNS, TLS, a CDN, or hosting-level redirects. Configure the hosting provider to:

- Redirect HTTP to HTTPS.
- Redirect `www.leonardalovric.com` to `leonardalovric.com`.
- Keep `/projects/{slug}/` mapped to its generated `index.html`.
- Return a real 404 response for missing routes and use `404.html` as the error document.
- Serve `.md` files as `text/markdown`, `.json` as `application/json`, `.txt` as `text/plain`, and `.xml` as `application/xml`.

The included `server/index.js` serves the built routes, including directory index pages, the correct machine-readable content types, and 404 status codes. Static hosts may require their own MIME, rewrite, and error-document settings. This repository does not configure any external infrastructure, so the apex and `www` redirect behavior must be verified after deployment.

Some experiments are rendered by interactive React components. Their page copy, source descriptions, and available media labels are included in the prerender, but the interactive controls and generated graphics still require JavaScript. No transcript or publication content is created where the source does not provide it. Search or AI systems may still omit, misinterpret, or fail to crawl public pages.

## Verification

Build and validate production files:

```sh
npm run build
npm run test:machine-readability
```

The test starts the production Node server and checks initial HTML content for the homepage and every project, page metadata, JSON-LD parsing, Markdown content types, sitemap links, crawler rules, JSON serialization, hidden editorial-field exclusion, and 404 responses. It does not execute JavaScript to extract page copy.

For a local production preview:

```sh
npm run preview -- --host 127.0.0.1 --port 4173
```

After deployment, verify the canonical pages, generated endpoints, HTTP status codes, crawler access, and apex/`www` redirects over HTTPS. The HTML, Markdown, and JSON responses should include all currently published source content without requiring JavaScript.
